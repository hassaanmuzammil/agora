# AGENTS.md

Instructions for AI coding agents working in this repository. See [README.md](README.md) for human-facing docs (architecture diagrams, features, setup).

## What this is

Agora is a self-hosted RAG chat app: Next.js frontend, FastAPI backend, Postgres (metadata) + MinIO (file blobs) + Qdrant (vectors), OpenAI for query rewriting and answer generation. Users upload PDFs, ask questions, get cited answers. Has role-based access control (admin/regular user + group-based file sharing).

## Repo layout

```
backend/app/api/       # FastAPI routers — auth, files, groups, threads, feedback
backend/app/rag/       # The actual RAG pipeline — read this before touching retrieval/generation
backend/app/rag/templates/  # query_rewrite.txt, final_answer.txt — tuned prompts, see below
backend/app/db/models.py    # SQLAlchemy models — source of truth for schema
backend/scripts/create_user.py  # Only way to provision a user (no signup endpoint exists)
frontend/app/           # Next.js App Router pages: /, /files, /groups, /thread/[id]
frontend/services/      # One typed API client per resource
frontend/hooks/         # One data-fetching hook per resource, mirrors services/
postgres/schema.sql     # Auto-applied to a fresh Postgres volume on first boot only
```

## Running it

Two supported setups — see [README.md#getting-started](README.md#getting-started) for full, tested instructions:

- **Full Docker**: `docker compose build && docker compose up -d`
- **Native app + Dockerized infra** (for active dev): `docker compose up -d postgres minio qdrant`, then run backend with `uv` and frontend with `npm run dev`

**Critical: run the backend from the repo root, not from inside `backend/`.** `backend.app.*` is imported as a package relative to the repo root — `cd backend && uv sync` to install deps, but then run `backend/.venv/bin/uvicorn backend.app.main:app --reload` from the repo root, not from inside `backend/`.

**After any code change to backend or frontend**, containers must be rebuilt to pick it up — there are no source volume mounts in `docker-compose.yml`:
```bash
docker compose build backend   # or frontend
docker compose up -d backend   # or frontend
```
There is no hot-reload in the Docker path. Use the native path (Path B in the README) if you're iterating quickly.

**Prompt template changes require a backend rebuild too** — `query_rewrite.txt`/`final_answer.txt` are read at import time and get baked into the image, same as any `.py` file.

## Non-obvious things that will bite you

- **`ensure_bucket()` doesn't run automatically unless `main.py`'s startup hook is intact.** If uploads start failing with an opaque 500 and no traceback in logs, check the MinIO bucket exists (`docker exec minio mc ls local/`) before assuming it's a code bug elsewhere.
- **`DATABASE_URL` differs by run mode.** The committed `.env` targets `localhost:5432` (for native runs); `docker-compose.yml` constructs its own container-network `DATABASE_URL` from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` rather than trusting `.env`'s value directly, specifically so the two modes don't clobber each other. Don't "simplify" this by making the containerized backend read `.env`'s `DATABASE_URL` verbatim — it'll break native mode or Docker mode depending on which hostname wins.
- **A native Postgres/MinIO/Qdrant already running on the host machine can silently intercept Docker's mapped ports** on `localhost`, especially Postgres — symptom is `role "postgres" does not exist` or similar auth errors despite Docker's container reporting healthy. Check with `lsof -i :5432` before assuming the app is broken.
- **`greenlet` is a required transitive dependency of SQLAlchemy's async engine, but its lockfile marker only lists `aarch64` (Linux ARM64), not `arm64` (what macOS reports on Apple Silicon)** — so `uv sync` on an M-series Mac silently skips installing it, and everything looks fine until the first DB query throws `ValueError: the greenlet library is required...`. It's declared as a direct dependency in `pyproject.toml` specifically to route around this; don't remove it even though it looks redundant with SQLAlchemy's own declared deps.
- **Don't run `npm install` locally against a lockfile generated by a different npm major version** — it can silently rewrite optional platform-specific entries (`@emnapi/*` and similar) in `package-lock.json`, which then breaks the Docker build's `npm ci` (strict, reproducible-only). If `frontend/package-lock.json` shows unexpected diffs after an install, prefer `git checkout -- frontend/package-lock.json` over committing the rewrite.
- **The Qdrant image is pinned** (`qdrant/qdrant:v1.15.1` in `docker-compose.yml`) to match `qdrant-client` in `backend/pyproject.toml`. If you bump one, bump the other, and expect to need a fresh `qdrant_data` volume if the on-disk format changed between versions (same caution applies to the Postgres image pin — see its comment in `docker-compose.yml`).

## The RAG pipeline — read before touching prompts or retrieval

This is the most failure-prone part of the codebase, tuned through extensive live testing. Full narrative in [README.md#rag-pipeline-deep-dive](README.md#rag-pipeline-deep-dive). Key invariants to preserve:

1. **`query_rewrite()` (`backend/app/rag/llm.py`) returns two separate fields, not one**: `search_query` (loose, retrieval-only) and `clarified_question` (faithful, same-scope, used only for the final answer). Do not collapse these back into one field — that was a real, reproduced bug (scope creep in the rewrite step broke answers that should have succeeded).
2. **The rewrite step's valid/invalid decision must never depend on whether we have documents on the topic.** It should only reject genuine non-questions (greetings, small talk, harmful requests, incoherent text). A well-formed question about an uncovered topic must pass through as valid — the "I don't have this" call belongs to the final-answer step, which actually reads the retrieved content.
3. **Both OpenAI calls use `temperature=0`.** This was added after proving via repeated identical-prompt testing that unset temperature caused the same prompt to sometimes answer correctly and sometimes falsely refuse. Don't remove this for "more natural" phrasing — it directly trades away answer consistency for cosmetic variety, and for a RAG QA system, faithfulness beats flavor.
4. **The final-answer prompt (`final_answer.txt`) explicitly permits partial-relevance context** ("use whichever chunks are relevant, ignore the rest, only refuse if none relate at all"). Without this, `expand_context=True` neighbor-chunk expansion (in `pipeline.py`) can dilute a good top-3 retrieval with tangential chunks and tip the model into a false refusal even when the answer was sitting right there in the context. If you see legitimate questions getting "I cannot answer" again, check this instruction hasn't regressed before assuming it's a retrieval-quality problem.
5. **Typo tolerance is intentional and example-anchored.** `query_rewrite.txt` includes a specific worked example ("smothquant" → "SmoothQuant") rather than a generic "watch for typos" instruction. This was tested head-to-head — three different generic rephrasings all performed the same or worse than the concrete example, on both the original bug case and on typos of terms never mentioned in the prompt. Don't genericize this without re-running that comparison.

## Testing changes

There's no automated test suite. Verify changes by hand against the running app:
- Auth/RBAC changes: log in as both `admin@example.com` and `user@example.com` (seeded via `create_user.py`, see README) and confirm access boundaries hold for both files and chat retrieval, not just the file list UI.
- RAG/prompt changes: test with a direct question, a pronoun-based follow-up in the same thread, a misspelled technical term, a greeting, and a question genuinely unrelated to any uploaded document — these five cases each exercise a different part of the pipeline and have each individually broken before.
- After any backend change, rebuild and restart the container (or use the native path) before testing — code changes are not live-reloaded in the Docker path.

## Security notes

- `.env` holds real secrets (OpenAI key, DB/MinIO credentials) and is gitignored — never read it into a commit, a log, or a response that might get persisted somewhere public.
- There is no rate limiting on `/threads/{id}/messages`. If asked to help expose this app publicly, flag that an unrate-limited endpoint calling a paid LLM API is a real cost/abuse risk before proceeding.
